P0 — 阻断交付已清零

这 11 条任一存在时，客户现场会出现「功能缺失 / 数据丢失 / 随机崩溃」级别的问题。全部已修复并通过构建。

P0-0已修复

布局切换销毁并重建 ExoPlayer（注释与实现相反）

现象
SINGLE → 2×2 → SINGLE 来回切，2/3/4 路被反复 release 重建，视频从 00:00 重播并闪黑。
根因
QuadPlayerLayout.kt 的 PlayerCell 在不可见时提前 return，令 MediaPlayerView 离开组合树，触发 VideoPlayerView 的 DisposableEffect.onDispose → release()。文件头注释却写明「布局切换不会重建」。
修法
隐藏格不再提前返回，始终组合播放器；隐藏时把配置改为「暂停 + 静音」以保留实例与进度，不再出声。
验证
切换布局时 logcat 不应再成对出现 Creating new ExoPlayer for: / Player released；切回后进度不回零。
P0-1已修复

客户版下 U 盘 btf_config.json 的功能开关全部失效

现象
Release 包中，U 盘 features 开关完全不生效。而 DEBUG_VS_RELEASE.md 明确承诺「在 U 盘根目录放置 btf_config.json 即可为客户开启功能」。
根因
MainScreen.kt 与 SettingsScreen.kt 在 customerUiMode 时无条件取 FeatureFlags.releaseDefaults()，把 FeatureManager 中已叠加过 U 盘覆盖的结果整个丢弃。Release 下该条件恒真。
修法
移除 UI 层的二次覆盖，改读 FeatureManager；底值差异由 FeatureManager.init(!customerUiMode) 决定。
验证
Release 包 + {"features":{"showImageSplitTool":false}} → 裁剪按钮消失；无 U 盘时行为与现状一致。
P0-2已修复

ERROR 状态不可逆 —— 播放恢复后 UI 永久卡在报错

现象
某路出现一次瞬时错误后，格子永久卡在报错，点播放/暂停也出不来，只能重选文件。
根因
setPlayerError 置 ERROR 后，togglePlayPause 的 else 分支对 ERROR 原样保留，updatePlayerCurrentIndex 只改索引不动状态。播放器自己却已在 STATE_READY 时清掉本地错误 —— 两套状态机各说各话。
修法
新增 onRecovered 回调链（播放器 → MediaPlayerView → QuadPlayerLayout → clearPlayerError），播放恢复即清除 ERROR。
验证
用无效路径播放 → 报错 → 换回有效文件，角标应由红转绿。
P0-3已修复

播放器初始化失败不上报，ViewModel 一直以为在播

现象
4 路并发下 ExoPlayer.Builder 抛异常时，格子显示「播放器初始化失败」，但角标仍是绿色 PLAYING，远控查询也回 playing。
根因
VideoPlayerView 的 exoPlayer == null 分支只渲染占位符就 return，唯独这一条漏了 onError 上报（同文件的「文件不存在」分支是有的）。
修法
该分支补 LaunchedEffect { onError?.invoke(...) }。
验证
人为让创建播放器抛异常，角标应变红且发出 sendError。
P0-4已修复安全

U 盘配置可经 usbScanFolderName 越出 U 盘读取任意目录

现象
U 盘上的 btf_config.json 写 "usbScanFolderName":"../.."，扫描目录即逃出 U 盘，把设备上任意目录的媒体拷入缓存，并持久化到设置长期生效。
根因
该字段只做「非空」校验，随后被 File(usbPath, folderName) 直接拼接，无规范化、无越界检查。
修法
解析层拒绝 .. / . / 含 / 或 \ 的值并记告警；使用层再用 canonicalPath 校验前缀，越界时回退到 U 盘根。
验证
新增单测覆盖 ../..、..、.、a/b、a\b、/sdcard 六种取值均被拒。
P0-5已修复

startForeground 失败被吞 → 系统在 5 秒后杀掉进程

现象
通知或渠道构造失败时，服务继续运行但无前台通知；Android 11+ 随后抛 RemoteServiceException 杀进程，日志上看着像「随机崩溃」。
根因
onStartCommand 与 onCreate 都把 startForeground 包在只记日志的 catch 里，随后照常返回。
修法
失败即 stopSelf() 并返回 START_NOT_STICKY，让失败可见而不是伪装成崩溃。
验证
注入通知构造失败，logcat 不应出现 RemoteServiceException，服务干净退出。
P0-6已修复

拷贝中断可能丢失全部旧缓存

现象
拷贝过程中断电/被杀，媒体只留在隐藏的 .playerN_backup；下次拷贝一进来先把它删掉 → 数据永久丢失。
根因
每次进入拷贝都无条件 backupDir.deleteRecursively()；异常路径既不恢复 backup 也不清理 staging。
修法
进入时先回收上次遗留的备份（若 target 缺失而 backup 存在则还原）；异常路径兜底还原 + 清理 staging。
验证
构造「backup 存在、playerN 缺失」，断言旧文件被找回而非被清掉。
P0-7已修复

拷贝可能并发执行，互相删毁 staging

现象
一次插盘触发两次拷贝，一个协程删掉另一个正在写入的 staging，两边都失败。
根因
USB 挂载广播被投递两次（Manifest 静态注册 + 服务内动态注册），而拷贝入口无单飞保护。
修法
copyMutex.withLock 串行化整批拷贝。
验证
并发调用两次 copyAllFromUsb，断言最终只有一份完整结果、无 staging/backup 残留。
P0-8已修复

ServiceConnection 泄漏

现象
Activity 在 bindService 与 onServiceConnected 之间被销毁时，logcat 报 Activity has leaked ServiceConnection，Activity 无法回收。
根因
onDestroy 只在 serviceBound（回调已到达）时才解绑，而该标志在此窗口内仍为 false。
修法
新增 bindRequested 标志，在发起绑定时置位，onDestroy 依据它解绑。
验证
触发绑定后立即 finish Activity，重复多次，logcat 无泄漏告警。
P0-9已修复

图片裁剪全量解码，4K/8K 源图必然 OOM

现象
选一张 8K 图点「执行裁剪」，进程直接闪退。峰值内存 ≈ 源图 + 各分块中间图。
根因
直接 decodeStream 全尺寸解码；且 catch (e: Exception) 抓不到 OutOfMemoryError（它是 Error 不是 Exception），崩溃无法拦截。 largeHeap 只是把崩溃点往后推。
修法
先 inJustDecodeBounds 读边界算出 2 的幂次 inSampleSize，使解码量不超过「分块数 × 目标分辨率」；并单独捕获 OutOfMemoryError 返回可读失败信息。
验证
8K 图跑 2×2，应显示「图片过大，内存不足」而非进程退出。
P0-10已修复

CI 在干净克隆上必然失败

现象
GitHub Actions 从未成功过；workflow 注定跑不起来。
根因
gradle.properties 硬编码 org.gradle.java.home=C:/Program Files/Android/Android Studio/jbr。runner 上不装 Android Studio，该路径不存在 → Gradle 直接报 Java home supplied is invalid，并覆盖掉 setup-java 设的 JDK。

删除该属性（本地需要时放进 ~/.gradle/gradle.properties）。
验证
干净目录执行 workflow 命令不再报 invalid Java home。

P1 — 影响交付质量

不阻断启动，但会造成现场功能异常、数据异常或难以排查的问题。

P1-01待修

图片裁剪把非 16:9 源图硬拉变形

现象
4000×3000 的 4:3 照片跑 2×2，每块裁出 2000×1500 后被无条件拉伸到 1920×1080，横向放大 1.33 倍，人脸明显变宽。
根因
只做等分，没有「先按目标总比例居中裁成 cols·16 : rows·9」的步骤，然后无条件 scale 到目标分辨率 —— 与注释声称的「确保输出全屏无黑边」矛盾。
修法
等分前先按 (cols×1920) : (rows×1080) 对源图做一次居中裁剪，再等分。
验证
4:3 与 16:9 两张图各跑 2×2，输出块宽高比应都等于布局理想比。
P1-02待修

裁剪结果不落布局，四路画面与裁剪网格对不上

现象
2×2 裁剪并应用后返回主页，墙仍是旧布局：若是 SINGLE 只有一格显示；若是「2×2 同画面」四格显示同一块，看着像没生效。
根因
应用时只写文件 + 重新加载媒体，从不设置 layoutMode / videoScaleMode。
修法
按 SplitLayout 映射到对应 LayoutMode 并写入设置，同时确保缩放模式为拉伸。
验证
2×2 裁剪应用后，settings.layoutMode 应为 GRID_2X2，四格各显示不同的一块。
P1-03待修

裁剪结果文件名带时间戳且从不清理，旧图混进轮播

现象
对图 A 应用一次、图 B 再应用一次，player1 目录下两张裁剪图并存，播放器在「旧图的一块」与「新图的一块」之间来回跳。多次应用后目录堆积大量历史文件。
根因
文件名带毫秒时间戳，永不重名也永不覆盖；写入前不清理同目录旧内容（对比 U 盘导入路径是有事务替换的）。
修法
写入前清空该播放器目录中的 split_*.jpg，或改用固定文件名覆盖写。
验证
连续应用两张图后，目录应只剩一份裁剪结果。
P1-04待修

裁剪失败后仍持有已回收的 Bitmap，再点保存即崩溃

现象
保存过程中某块写盘失败时，页面停留且预览仍在渲染已回收的位图 → Canvas: trying to use a recycled bitmap 崩溃。且按钮仍可用，再按一次会弹「已保存 N 块」的假成功。
根因
回收后仍把同一批位图对象写回状态；失败分支只回调 onComplete(false) 而不清空结果；按钮 enabled 只看上一次的 success。
修法
成功/失败路径都清空结果或改为只持有路径的轻量模型；保存中禁用按钮；savedCount 统计本次实际写入数。
验证
把目标目录设为只读后保存，应提示部分失败而非崩溃；连点两次不出现成功提示。
P1-05待修

裁剪忽略 EXIF 方向，输出与预览方向不一致

现象
手机竖拍照片（EXIF Orientation=6）预览是竖的、网格也竖着画，但裁出的四块是横的，拼起来和预览完全对不上。
根因
裁剪走 BitmapFactory.decodeStream（不解析 EXIF），而预览用 Coil 的 AsyncImage（会按 EXIF 自动定向）；读尺寸也是未旋转的宽高，导致推荐布局判错横竖。
修法
解码后读 TAG_ORIENTATION 并做矩阵旋转；getImageInfo 按 EXIF 交换宽高后再推荐布局。
验证
用 Orientation=6 的照片跑 2×2，输出块方向应与预览网格一致。
P1-06待修

裁剪整除余数被丢弃，写盘非原子会残留半截文件

现象
4001×3001 的图跑 2×2，最后一列/行各丢 1px。磁盘满时目录里留下几百字节的半截 split_*.jpg，因长度 > 0 仍被收进播放列表，播放时黑屏。
根因
sourceWidth / cols 整数除法余数不补偿；写盘直接 FileOutputStream，中途异常不删除半成品。
修法
边界改为 left = col * w / cols、right = (col+1) * w / cols 让整图无遗漏；写盘先写 .tmp 再 rename。
验证
4001×3001 跑 3×1，三块宽度之和应为 4001；填满分区后目录无半截文件。
P1-07待修

视频索引与媒体总索引混用，混合内容时切错视频

现象
一路里同时有视频和图片时，图片轮播推进过的序号会污染视频索引，下次切视频跳到错误文件或回到第一个。
根因
MediaPlayerView 用 videoItems 的索引空间，而 ViewModel 用 mediaItems 的索引空间读写同一个 currentIndex 字段；错误回退分支又把它当图片索引用。
修法
统一 currentIndex 语义为「在 mediaItems 中的下标」，由 MediaPlayerView 内部做映射；或为视频/图片各设独立字段。
验证
构造「2 视频 + 5 图片」，触发视频结束与图片回退各一次，上报下标应与实播文件一致。
P1-08待修

轨道选择无上限，4 路 4K 有 OOM 与解码器耗尽风险

现象
4 路同时打开高码率 4K HEVC 时内存攀升、卡顿甚至被杀。
根因
DefaultTrackSelector(context) 未设 setMaxVideoSize / setMaxVideoBitrate，选流阶段就允许 2160p；缓冲字节数也设为 LENGTH_UNSET，随分辨率自动放大。
修法
用带约束的 Parameters 构造选择器（上限做成可配置项而非硬编码无限）；缓冲字节数改为固定上限。
验证
4K 源四路同开，dumpsys meminfo 观察峰值，dumpsys media.codec 确认活跃解码器数。

UI 层大量硬编码中文，绕过 StringResources

P1-11待修

set_loop_mode 非法值静默降级；set_interval 回报未 clamp 的值

远控发 {"action":"set_loop_mode"}（缺字段）或非法值，一律静默变成 LIST 并回报成功；set_interval 999 实际生效 60，回执却写 999。

P1-12待修

播放器级命令对不存在的索引仍报成功并广播虚假状态

现象
SINGLE 布局下发 play(player_index=3)，回执报 playing，实际什么都没发生；远控端据此认为 4 路都在播。
根因

验证

P1-13待修

错误码塌缩：1004 / 1005 永不触发，部分失败静默

现象
「文件不存在」「不可读」「格式不支持」三种情况一律折叠成同一个错误码；media_paths 数组里部分路径无效时只记日志跳过，调用方收到「成功 + 更少文件」。
根因
createMediaItem 用 null 表示所有失败原因；两个已声明的错误码全仓零引用。
修法
改为密封结果类型区分三种失败并映射到对应错误码；数组部分失败返回 false 并列出被跳过的路径。
验证
分别用不存在路径、无读权限文件、.txt 构造命令，断言错误码各不相同。
P1-14待修

hide / show 无投递确认即报成功

现象
Activity 不在前台时发 hide，广播无人接收、应用并未退到后台，调用方却收到 command_success。show 同理（后台启动 Activity 受限）。
根因
两个 handler 只负责发送广播或 startActivity，发送成功即视为命令成功，无回执确认。
修法

验证

P1-15待修文档

11 种状态事件全部未文档化，state 取值域不一致

根因

验证
契约测试：stop 命令的 playback_changed.state 应与随后 get_status 中该路取值一致。
P1-16待修

状态载荷泄漏本地绝对路径

现象
media_path 在三类事件中外发原样绝对路径（含 U 盘挂载点）；错误消息也内嵌路径。
根因
直接透传内部路径，未做脱敏。
修法

P1-17待修

batch 无深度限制可致栈溢出，部分失败仍报成功

现象
嵌套 batch 无层数限制，递归过深会在主线程抛 StackOverflowError 崩溃进程（catch Exception 抓不到 Error）。10 条子命令产生 11 次系统广播。部分失败时仍回报成功。
根因
递归调用未限深度；catch 范围不含 Error；成功计数与总数未比对。
修法
加深度上限（如 >3 拒绝）；catch 扩到 Throwable；部分失败改发错误或聚合上报（子命令进入静默模式，结束时一次性汇总）。
验证
5 层嵌套不崩溃且返回 false；10 条子命令只产生 1 次广播。
P1-18待修

主线程阻塞 I/O —— 大目录扫描有 ANR 风险

现象
远控 set_media_dir 指向含上万文件的目录时，广播接收器在主线程同步 listFiles() + 逐文件 exists/canRead/length，receiver 有约 10 秒超时。
根因
onReceive 默认主线程；handler 未切到 IO。
修法
改用 goAsync() + 后台调度，或 handler 内对扫描切 Dispatchers.IO，结果回调中再发广播。
验证
万级文件目录下发送命令，主线程无 >100ms 停顿。
P1-19部分修复

图片 96MB/格：Size.ORIGINAL 关闭了降采样

现象
4 路图片轮播大图时内存暴涨、切图卡顿。6000×4000 按 ARGB_8888 解码约 96MB，淡入淡出期间新旧两份同时驻留再乘 4。

修法

验证
4 路轮播大图，dumpsys meminfo 的 Graphics 峰值应显著下降。
P1-20待修

P1-21待修

模式按钮文字可能被硬裁（无 ellipsis）

U 盘配置写入非客户模式时，拼接区无任何高亮

U 盘配置写 layoutMode: "PIP"（合法枚举但不在客户可见集合内），设置页 8 个按钮全为未选中色，用户看不到当前模式，随便一点就覆盖掉配置。

P1-23待修

开机自启不可靠

现象

P1-24待修

权限被拒后 U 盘功能永久静默失效，无重试入口

现象
用户在系统页拒绝「所有文件访问」后返回应用，U 盘监听服务永不启动，插拔 U 盘无任何反应，界面无提示也无重试入口。
根因
权限判定只在 onCreate 调一次，onResume 不复查；拒绝分支只弹一次 Toast 就跳转系统设置。
修法
抽出权限检查在 onResume 复查；未授权时禁用/降级 U 盘相关 UI 并给出「重新授权」按钮；授权成功后补启动服务。
验证

P1-25待修

拷贝前空间检查口径不对，未计入事务的瞬时占用

现象
检查通过后拷贝仍可能因空间不足失败；「覆盖确认」这条路径完全没有空间检查。
根因
所需空间按整个目录树字节数整除 MB 计算（截断且把不支持的文件也算进去）；而事务本身要求 staging 与旧缓存/backup 同时存在，峰值约需 2 倍。
修法
只统计受支持且非空的文件字节；拷贝前用目标分区剩余空间做 required × 2 > free 的硬校验。
验证
构造「需要 2X、可用 1.5X」，决策应为空间不足而非直接拷贝。
P1-26待修

源端文件减少时旧缓存永不清理，缓存可无限增长

现象
U 盘只剩 player1 时，player2/3/4 的旧缓存原样保留并继续被扫出来播放；裁剪产生的 split_*.jpg 无任何删除路径，每裁剪一次就往四个目录各塞一份。
根因

修法

验证
首次拷贝 player1+player2，第二次只拷 player1，断言 player2 目录为空。

P2 — 体验与可维护性

不影响正确性，但会造成现场困惑、维护成本或长期隐患。

P2-01待修

showDebugInfo 是僵尸开关

现象
该开关在 FeatureFlags、UsbConfig、四份文档与样例配置里都有，但 app/src/main 中零处读取 —— 集成方改了没有任何效果。另有三个同类的僵尸字段：useHardwareDecode、audioOutput、usbDetectionEnabled、maxCacheSizeMB、showCopyProgress。
修法
逐项「接线或删除」：需要生效的接上实现，不需要的从模型、解析、文档、样例四处一起删掉。
验证
每项 grep 应存在非 UI 的消费点，或该字段已不存在。
P2-02待修

U 盘下发的设置覆盖被永久写进 DataStore，拔盘不还原

现象
插带 settings.layoutMode 的 U 盘 → 生效；拔掉后布局仍是被覆盖的值，且此后每次冷启动都保持 —— 与「清除 U 盘配置即恢复」的契约矛盾，也无法区分「用户手动设置」与「U 盘强制」。
根因
U 盘设置被单向写入持久层，不记录覆盖前快照，无回滚路径。
修法
把 U 盘下发的设置改为运行时覆盖层（内存 overlay），或在应用配置前保存快照、清除时回滚。
验证
记录覆盖前的 layoutMode，插盘改配置，拔出后读持久层应等于快照值。
P2-03待修

冷启动时已插着的 U 盘，settings 覆盖不会应用

现象
设备重启前 U 盘保持插入，开机后 features 覆盖生效，但 settings 覆盖（布局等）不生效。
根因
settings 覆盖的唯一入口是「U 盘刚连接」回调；而启动时走的是「同步已连接状态」路径，只更新状态不应用配置；服务侧的配置加载回调在 Activity 绑定前触发，事件已丢失。
修法
在同步已连接状态的路径上补一次幂等的配置应用，或在绑定完成后主动应用一次。
验证
保持 U 盘插入重启应用，日志应出现「应用U盘配置设置」且布局正确。
P2-04待修

USB 状态有两个独立数据源，拷贝成功会强制改回已连接

现象
拷贝中途拔盘，服务已发出「已断开」，但 ViewModel 的拷贝回调随后把状态写回 Connected，界面显示「U 盘已连接」而实际已拔出，后续逻辑继续使用失效路径。
根因
服务与 ViewModel 各持一份状态；补偿通道是四个散装 setter，且回调在 ViewModel 引用就绪前会静默丢事件。
修法
让服务侧成为唯一数据源，ViewModel 只转发；删除 ViewModel 内的状态写入，改为「拷贝开始时捕获路径 + 完成时校验当前状态」。
验证
大文件拷贝中拔盘，界面应在 1 秒内变为已断开且不回弹。
P2-05待修

已连接状态不重扫；错误状态无退出路径

现象
插入无 media 目录的 U 盘后，现场补建该目录，界面仍停在「未找到目录」直到手动扫描或重插；「空间不足」这类错误状态也会无限持续。
根因
同一路径的已连接状态不触发重新检查；错误状态只由 ViewModel 发出，服务端不会纠正。
修法
对「已连接但无媒体/无配置」的情况周期性重扫；给错误状态一个退出路径。
验证
插入无 media 的 U 盘，用 adb 补建目录，一个扫描周期内状态应自动翻转。
P2-06待修

状态事件字段无版本号；interval_seconds 命名有歧义

现象
接入方无法做版本协商；interval_seconds 的字面意思像「状态推送周期」，实际是图片轮播间隔，极易误用。全仓无心跳事件。

载荷加 schema_version；字段改名（保留旧名一版兼容）；文档明确「无周期心跳，存活信号仅 app_started / app_stopping」。

客户版底部栏是否应显示「扫描U盘 / 裁剪」

现状
客户版分支没有读取这两个按钮的开关，而默认配置里「扫描U盘」是开启的 —— 可能是遗漏，也可能是刻意精简。注意 1024px 宽度下再加两个按钮需要重新分配宽度。
DEC-3待决策

拼接板示意图与 App 的行列记法相反

现状
示意图上手写的模式 5/6/7 标注用「列×行」，App 内显示「横屏 2×1」用「行×列」，所指画面相同但记法相反。因为涉及客户可见文案，本版未动。
DEC-4待决策部署

HDMI 硬件按键需要 ROM 放权才能用

现状
控制节点权限为 root 只写，普通应用写入被拒（SELinux 为 Permissive，纯属文件权限）。这是内核/驱动与 ueventd 决定的，应用层无论用什么 API 都在同一道 VFS 检查之下，无法在 App 内修复。
选项
① ROM 侧把节点权限放开（一行 chmod，最省事）；② 把应用放进系统私有分区；③ 若客户不改 ROM，则把这两个按钮从客户版隐藏，避免现场把「点了没反应」误判成软件缺陷。
