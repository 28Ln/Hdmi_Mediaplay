# 审计存档与增量扫描规范

> **目的**：避免同一问题被反复扫描、反复修复。
> 每次审计都在 `docs/audits/` 下留一份**带代码指纹的结论**，
> 下次扫描前先比对指纹 —— 代码未变的部分直接沿用结论，不再重扫。

---

## 一、为什么需要

本项目此前的审计存在三个问题：

1. **结论分散且互相矛盾** —— `audit-findings.md` 与 `audit-checklist.html`
   对同一审计给出 4 / 11 两种 P0 计数，编号体系还不通用
2. **无指纹，无法判断是否失效** —— 文档写「已修」但代码可能后来被改回，
   下次审计只能从头再扫一遍
3. **重复劳动** —— 同一个问题（如「设置页滚不动」）被反复诊断，
   因为上一次的结论没有沉淀成可复用的记录

---

## 二、存档结构

```
docs/audits/
├── README.md                 ← 本文件（规范）
├── INDEX.md                  ← 所有审计记录的索引与当前有效状态
├── 2026-10-15-audit-01.md    ← 首次全量审计（20 agent）
├── 2026-10-17-audit-02.md    ← 二次审计（验证批量改动）
└── ...                       ← 后续每次一份
```

### 每份记录必须含

| 字段 | 说明 |
|---|---|
| `审计日期` | 绝对日期 |
| `代码指纹` | 审计时 `HEAD` 的 commit SHA |
| `范围` | 扫了哪些模块/文件 |
| `方法` | 人工审 / agent 并发 / 真机实测 |
| `结论` | 发现的问题（带 file:line） |
| `已修复` | 本轮修了什么（带证据） |
| `未修复/待决策` | 明确列出，避免下次重复发现 |
| `失效条件` | 什么情况下这份结论需要重扫 |

---

## 三、增量扫描规则

### 扫描前必做

```bash
# 1. 看当前 HEAD
git rev-parse --short HEAD

# 2. 读 INDEX.md，找出上次审计的 commit SHA

# 3. 只扫这两者的差异部分
git diff --stat <上次审计SHA>..HEAD
```

### 判定规则

| 情况 | 处理 |
|---|---|
| 上次结论涉及的文件**未变** | **直接沿用结论**，不重扫 |
| 结论涉及的文件**已变** | 只重扫这些文件 |
| **新增文件** | 需要扫描（不在任何既往结论中） |
| 结论中标注「待决策」的项 | 除非用户决定，否则**不重复扫描**（已记录，非未知） |
| 结论中标注「评估后不做」的项 | **永不重扫**，除非用户明确要求 |

### 结论失效的判定

一条「已修复」结论在以下情况失效，需要重新验证：

- 其证据文件（file:line）在后续 commit 中被修改
- 对应的测试被删除或跳过
- 该修复依赖的外部条件改变（如 ROM 行为变化）

## 五、审计代理的使用规范

本项目的审计使用并发 agent（曾用 20 个只读 agent 做过全量扫描）。
为避免重复劳动，agent 的 prompt 中**必须**包含：

1. 指向 `docs/audits/INDEX.md`，要求先读既有结论
2. 明确「已评估过、不要重复报告」的清单（见上节）
3. 要求输出**带 file:line 的结论**，便于下次比对指纹

### 反面案例（本项目真实发生过）

- 用 20 个 agent 全量扫描，得出 59 项发现 —— 但其中多项在此前已经修过，
  因无存档记录而被重复发现
- 反复用 `adb input swipe` 测滚动，结论总是「正常」，
  因为该方法走触摸源、测不出鼠标拖动问题 —— **方法论错误导致重复无效验证**

## 六、记录模板

新建 `docs/audits/YYYY-MM-DD-audit-NN.md`：

```markdown
# 审计记录 NN

- 审计日期：YYYY-MM-DD
- 代码指纹：`<commit SHA>`
- 范围：
- 方法：

## 结论

### 新发现
| 编号 | 问题 | 位置 | 级别 | 状态 |

### 验证既有结论
| 编号 | 上次结论 | 本次验证 | 是否仍成立 |

## 本轮修复
| 编号 | 修复内容 | 证据 |

## 待决策 / 待外部输入

## 失效条件
（什么情况下本记录需要重扫）
```
