### 新发现 0（P0 级回归）：`LocalStorageManager` 备份清理被写反，导致 U 盘拷贝**永久失败**

**位置**：`data/local/LocalStorageManager.kt:128`（`6d5cf53` 引入）

```kotlin
stagingDir.deleteRecursively()
if (!backupDir.exists()) {      // ← 条件写反
    backupDir.deleteRecursively()
}
```

**这是本轮最严重的发现，且完全由批量/粗心编辑造成**：

- 原实现是**无条件** `backupDir.deleteRecursively()`（清理陈旧备份）
- 加条件后，删除只在「目录不存在」时执行 → **恒为空操作**
- 编译通过、无告警、无测试失败，**症状只有在真实拷贝被中断后才会暴露**

**故障链**（报告已逐行核实，我独立复核确认）：

1. 某次拷贝在 promote 成功之后、清理之前被杀（断电 / 进程被杀）→
   `localPlayerDir` 与 `backupDir` **同时存在**
2. 下次拷贝：第 120 行的孤儿还原分支要求 `!localPlayerDir.exists()`，**跳过**；
   第 128 行的守卫因 `backupDir` 存在而**跳过删除**
3. 第 158 行 `localPlayerDir.renameTo(backupDir)` —— `renameTo` **无法覆盖已存在的目录**，
   返回 false → `backup_prepare_failed`
4. **此后每一次 U 盘拷贝都失败**，且必须手工删除隐藏目录 `.playerN_backup` 才能恢复

**顺带修掉的第二个隐患**：孤儿还原失败（第 122 行 `renameTo` 失败）时原代码只记日志、
继续往下走，而紧接着的 `backupDir.deleteRecursively()` 会删掉**当时唯一一份数据**。
现已改为：还原失败即中止拷贝并返回 `backup_recovery_failed`，绝不删除。

**修复**：恢复无条件删除，并加注释说明为何**不能**加 `exists` 条件。

**为何没被测试挡住**：该路径需要「拷贝中途被杀」才能触发，任何单元测试都不会覆盖。
这类缺陷只能靠**逐行比对行为**发现 —— 正是本次二次审计的用途。

### 新发现 1：P1-26 只修了一半（真实缺陷，已修）

P1-26 的修复只覆盖了 `PlayerCommandHandler.kt`，**`UsbConfig.kt` 仍是裸调用**：

| 位置 | 代码 | 后果 |
|---|---|---|
| `UsbConfig.kt:107` | `value.uppercase()` | tr-TR 下 `"pip"` → `"PİP"` ≠ 枚举 `"PIP"`，合法配置被静默判为非法并回退默认值 |
| `UsbConfig.kt:124` | `value.lowercase()` | tr-TR 下 `"I"` → `"ı"`，别名匹配失败 |

**危害等级**：该缺陷**不报错、不崩溃**，只是 `validationWarnings` 里多一条告警、
配置项回退默认值 —— 客户在土耳其语设备上会看到「配置写了不生效」，
且排查时会误以为是自己配置写错了。

**本轮修复**：三处改用 `Locale.ROOT`（`uppercase`/`lowercase`/十六进制归一化），
并新增 2 个回归测试固化：
- `enum normalization is immune to turkish locale`
- `config parsing under turkish locale still accepts valid enum values`

> 测试在 `Locale.setDefault(tr-TR)` 下运行并在 `finally` 中还原，
> 因此**在中文/英文 CI 上也会真实覆盖这条路径**，不是摆设。

### 新发现 2：`hide` 不仅没修好，还比修之前更差（已修）

`2cbd473` 把 `hide` 改成「注册回执接收器 → 发广播 → `latch.await(1s)`」。
**该方案不可能成功**，两个独立原因：

1. **`onReceive` 里不能注册接收器**：命令由 `PlayerCommandReceiver.onReceive` 发起，
   该上下文是 `ReceiverRestrictedContext`，`registerReceiver` 会抛
   `ReceiverCallNotAllowedException`。`ContextCompat` 无法绕过（文档化的框架限制）。
2. **主线程互锁**：命令处理本身在主线程；回执也在主线程投递 → 主线程正阻塞在
   `await` 上，回执永远送不到 → 必然 1 秒超时。

**更严重的副作用**：`registerReceiver` 排在 `sendBroadcast` **之前**，异常被外层
`catch` 吞掉 → **连「退到后台」这个动作都不再执行**。对比修改前（发广播即返回），
`hide` 从「可能不生效」变成「**保证不生效**」。

**本轮修复**：改用 `util/AppForegroundState` 在**发送前**同步判定前台状态
（由 `MainActivity.onStart/onStop` 维护）：
- 不在前台 → 返回 `1006`，不谎报成功
- 在前台 → 发广播并返回成功（广播异步投递，副作用由 Activity 完成）

同时删除已无意义的回执常量 `ACTION_MOVE_TO_BACK_ACK` 与相关代码。

### 新发现 3：P1-27 只拦了「无媒体」，没拦「不在当前布局」

`_playerConfigs` 恒为 4 项且**不随布局收缩**（隐藏格子仍需保留 ExoPlayer 实例与进度，
见 `QuadPlayerLayout` 注释），因此 `configs.getOrNull(index) != null` **不能**用来
判断索引是否有效。

后果：`SINGLE` 布局下对 `player_index=3` 发 `play`，只要该路有媒体就会返回成功，
并向信发系统广播一个**并不存在**的 `playing` 状态。

**同类问题**（本次一并修）：

| 命令 | 原行为 |
|---|---|
| `play_all` | 一路可播内容都没有时仍报成功 |
| `pause_all` | 没有任何路在播放时仍报成功 |
| `stop_all` | 无条件报成功 |
| `set_volume` / `set_mute` | 索引不在布局中时空操作，仍报成功 |

**本轮修复**：`ViewModelCallback` 的 `playAll` / `pauseAll` / `stopAll` /
`setVolume` / `setMute` 改为返回 `Boolean`，`MainViewModel` 按实际生效情况返回，
handler 据此在未生效时返回错误（`1001` / `1006`）。

### 新发现 4：契约文档 8 处与代码不符（已修）

验证 agent 逐字段核对 `PlayerStatusBroadcaster` 后发现，其中**最致命的一处**是：

| 文档写的 | 代码实际发的 | 影响 |
|---|---|---|
| `players[].player_index` | `players[].index` | **接入方按文档写会取不到值**，状态列表整体无法绑定 |

其余已修：`media_type` 未文档化、顶层 `timestamp` 未文档化、
错误码表漏 `5001`（播放期错误，实际会被发出）、
`1004/1005` 被错标为「不会发出」（实际已由 `set_media` 发出）、
`2002` 的含义不含「参数值非法」、§六 声称已修但实际未修的条目。

**教训**：文档里每一条「✅ 已修复」都必须在**代码里找到对应实现**才能写，
不能凭记忆或凭提交信息。本次 §六 的 `hide` 条目就是反例。

### 新发现 5：`HelpTip` 切语言后不刷新（真实缺陷，已修）

`StringResources` 是普通单例、**不是** Compose State，
因此 `HelpTip(lang = settings.language)` 里的 `lang` 虽被传入却从未参与取值，
语言切换不会触发该组件重组 —— 帮助提示会停留在旧语言。
（此前它只表现为一条 `Parameter 'lang' is never used` 编译告警，容易被当成噪音忽略。）

**修复**：用 `key(lang) { HelpTipContent() }` 把它作为重组键接入。

> 反向教训：验证 agent 建议「删掉未使用的 `lang` 参数」，
> 若照做会把这条真实缺陷**变成永久缺陷**。未使用告警有时指向的是漏接线，不是死代码。

### 已知不完整（**不要当成已修**）

`res/values-en/strings.xml` 已创建并可正常打包，但**它不会让通知跟随应用内语言设置**：
应用从未调用 `AppCompatDelegate.setApplicationLocales` / `LocaleManager`，
语言切换只作用于 `StringResources` 这个 Kotlin 单例；
而 Android 解析 `R.string.*` 用的是**系统语言**，不是应用内选择。
因此「系统中文 + 应用内英文」时，通知标题/正文仍是中文。

要真正生效需接入 `setApplicationLocales`（并视需要配 `android:localeConfig`），
这是一处**代码改动**，本轮未做，故在此明确记录，避免下次被当作「已完成」而跳过。

### 专题：设备过热与四路播放

**实测数据**（2026-10-17，RK3568 / 1024×600 / 四路 2×2 播放中）：

| 传感器 | 温度 |
|---|---|
| `soc-thermal` | **85.0 °C** |
| `gpu-thermal` | **85.6 °C** |

该温度已进入 SoC 降频区间。此时解码速率下降，四路之间的漂移会**加速**，
表现为掉帧、缓冲变慢、越播越不同步。**这不是 App 逻辑缺陷，是热设计问题。**

**关键线索**：解码器为硬解 `OMX.rk.video_decoder.avc`，但日志持续出现

```
E ACodec: [OMX.rk.video_decoder.avc] setPortMode on output to DynamicANWBuffer failed w/ err -1010
E OMXNodeInstance: getParameter(...) ERROR: UnsupportedIndex
E OMXNodeInstance: setConfig(ConfigPriority) ERROR: UnsupportedIndex
```

`DynamicANWBuffer` 设置失败意味着**硬解输出无法走零拷贝直通路径**，
退回到额外内存拷贝 —— 这会同时抬高 CPU 占用与发热。
**建议 ROM 方核对解码器 HAL 与 gralloc 配置**，这是 ROI 最高的一项。

**App 侧可做但本次未做**（需真机温度对比验证，不能凭猜）：

| 手段 | 预期 | 风险 |
|---|---|---|
| 降低 `MAX_VIDEO_WIDTH/HEIGHT` | 减少解码像素量 | 客户若确需高清源会画质下降 |
| 单路播放时放宽、四路时收紧（按布局动态计算） | 兼顾 | 实现复杂度中等 |
| 限制同时解码路数（如 >2 路时降为 720p） | 明显降载 | 需产品接受画质取舍 |
| 播放器 `resizeMode` 保持 SURFACE 而非 TEXTURE | 避免 GPU 拷贝 | 已默认 SURFACE，无需改 |

**重要**：以上均为**推断**，未在真机做温度对照实验。改动前应先做
「改参数前后各测一次 `soc-thermal`」的 A/B，否则可能只是心理安慰。

## 五、方法论教训（补充）

| 教训 | 说明 |
|---|---|
| **修缺陷要 grep 全部同类调用点** | P1-26 只修了报出问题的那一处，`UsbConfig.kt` 的同类调用被漏掉近一个月，且**无任何症状**（只是告警多一条）。修复一个模式时，必须全仓搜同一模式 |
| **台账本身会漂移** | 同一问题在 P1 已修、P2 又列一遍；「别名」被当成「缺陷」登记。审计不仅要核代码，也要核**台账与代码的一致性** |
| **回归测试要能真实覆盖路径** | `Locale` 类缺陷若只在特定环境触发，测试必须**主动设成该环境**（并 `finally` 还原），否则在 CI 上永远是绿的、永远测不到 |
