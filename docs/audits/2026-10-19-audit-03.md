## 一、本轮实测环境（可复现）

原 API 35 AVD 是 `google_apis_playstore` 镜像，**adbd 不能 root、无 su、SELinux 阻止访问
`/mnt/media_rw`**，所以 U 盘链路确实测不了。本轮换装了可 root 的镜像：

```bash
# 1. 安装 Android 11 google_apis（userdebug，adb root 可用）
sdkmanager "system-images;android-30;google_apis;x86_64"
# 2. 手工建 1024x600@160 的 AVD（avdmanager 对该镜像报 "Package path is not valid"，故手写 config.ini）
#    .android/avd/RK3568_API30.avd/config.ini
#    image.sysdir.1 = system-images\android-30\google_apis\x86_64\
#    hw.lcd.width=1024 hw.lcd.height=600 hw.lcd.density=160
# 3. 启动
emulator -avd RK3568_API30 -no-snapshot-save -no-boot-anim -gpu swiftshader_indirect
adb root        # 成功：adbd is already running as root
```

### 造「假 U 盘」的可行做法（**这条要写进后续验证指南**）

`/storage` 与 `/mnt/media_rw` 本身都不可写，但 **root 可以 bind-mount**：

```bash
adb root
adb shell 'mkdir -p /data/local/tmp/fakeusb/media/player{1,2,3,4}'
adb shell 'mkdir -p /mnt/media_rw/FAKEUSB'
adb shell 'mount --bind /data/local/tmp/fakeusb /mnt/media_rw/FAKEUSB'
adb shell 'umount /mnt/media_rw/FAKEUSB'     # 模拟拔盘
```

`UsbUtils.getMountedUsbPaths()` 直接扫 `/mnt/media_rw`，因此应用会把它当作 U 盘。

> 若换回 `google_apis_playstore` 镜像（不可 root），则只能用 `-sdcard <img>` 挂 public volume，
> 但那条路径受 SELinux 限制（`avc: denied { open } path="/mnt/media_rw"`），
> 应用**看不到** `/storage/<UUID>` 下的内容。**结论：U 盘链路验证必须用 userdebug 镜像。**

### 缺陷 1（已修）：空间不足时残留覆盖确认框

复现：`truncate -s 9G` 造一个稀疏大文件放进 U 盘 → 重新插入。

现象：顶部出现红色「存储空间不足！需要 9.20 GB，可用 5.43 GB」，
**但上一次插入留下的「检测到U盘内容」对话框仍然盖在画面上**。

根因：`_showOverwriteDialog` 是独立 StateFlow，
`onUsbConnected` 把决策从 `RequireOverwriteConfirmation` 改成
`InsufficientSpace` / `NoMediaContent` / `CopyImmediately` 时，
没有任何代码把该标志复位。

修复：`MainViewModel.dismissPendingOverwrite()`，在**除「需要确认」以外**的
三个分支里调用（`MainViewModel.kt`）。修后复测：红色提示出现，**无残留对话框**。

### 缺陷 2（已修）：错误自动重试的指数退避**永远退化为固定 5 秒**

这是本轮最重要的一条 —— 单测是绿的（`usbRetryDelayMs` 本身正确），
但端到端行为完全相反。

**实测证据**（API 30，9GB 稀疏文件触发空间不足）：

```
22:30:30.268  Manual scan triggered
22:30:40.910  Manual scan triggered   ← +10.6s
22:31:01.289  Manual scan triggered   ← +20.4s
22:31:41.883  Manual scan triggered   ← +40.6s
22:32:42.388  Manual scan triggered   ← +60.5s（封顶）
```

修前同一场景的间隔**恒为约 5.3 秒**，跑多久都不增长。

**根因（两处叠加，且都是"看起来合理"的代码）**：

1. `UsbMonitorService` 每次检查都会 `emitUsbState(Connected)`，
   经 `onUsbStateChanged` → `MainViewModel.syncUsbState()`；
2. 旧 `syncUsbState()` 只要收到**非 Error** 状态就 `resetUsbRetryBackoff()`；
3. `enterUsbErrorState()` 里还有一个 `delay(3000)` 后「状态不是 Error 就清零」的
   兜底逻辑。

问题在于：**空间决策要读磁盘、统计四个目录大小，常常超过 3 秒**。
于是重试流程变成：

```
retry 协程 ++attempt → rescan()
  服务 emit Connected  → syncUsbState 清零 attempt（协程也被 cancel）
  ...几秒后... onUsbConnected 仍判定空间不足 → enterUsbErrorState
  → attempt 已回到 0 → 又是 5 秒
```

**修复**：引入 `usbErrorActive` 标志，**不再用 `_usbState.value is Error` 判断**。
只由明确的恢复信号清除：`onUsbConnected` 的决策不再是 `InsufficientSpace`，
或收到 `Disconnected`。同时删除 `delay(3000)` 的兜底判断。

修后复测：间隔按 5→10→20→40→60 增长并封顶，与 `usbRetryDelayMs` 一致。

> 这条再次印证了 `INDEX.md` 的教训：**纯函数单测覆盖不了「状态机与异步时序」**。
> `usbRetryDelayMs` 的单测永远绿，因为它从不参与「什么时候该清零」这个决策。

### 缺陷 3（已修）：从后台返回时覆盖确认框重放

复现：对话框弹出时按 Home → 再切回应用。

现象：确认框**再次弹出**（且 `pendingUsbPath` 被覆盖）。

根因（两条叠加）：
1. `UsbMonitorService.onUsbConnected` 的 **setter 有回放副作用**：
   每次赋值都会把 `lastDetectedUsb` 再投递一次（`UsbMonitorService.kt`）；
2. `MainActivity.onResume` 每次都调用 `setupServiceCallbacks()` → 重新赋值回调 → 触发回放。

**第一次修复是错的**（值得记录）：按「路径 + hasMedia 去重」。
实测发现它把**真实的重新扫描也挡掉了** —— 往 U 盘加了 9GB 文件，
日志显示 `去重（同一盘已在本次会话处理过）`，检查根本没跑。
原因：内容变化与回放走的是**同一条回调路径**，无法用参数区分。

**最终修复**（两层，都是"消除触发条件"而不是"过滤结果"）：
1. `UsbMonitorService` 增加 `replayPending`：只有真实检测事件
   （`notifyUsbConnected`）才置 true，回放一次后置 false；拔盘置 false。
   这样「开机后补发一次」仍有效，但重复 set 回调不再重放；
2. `MainActivity.callbacksInstalled`：回调只安装一次，`onResume` 只做无副作用的
   状态同步，不再重复赋值；`onStop` 解绑时复位。

修后复测：Home → 返回，界面停在主画面，**确认框不再出现**，日志无回放记录。

### 缺陷 4（已修）：U 盘下发的设置**永久留驻**，拔盘后不回滚

复现：U 盘放 `btf_config.json`（`layoutMode=GRID_1X2`、`defaultVolume=10`、
`imageIntervalSeconds=9`）→ 插入 → 拔盘。

修前行为：布局**仍是 1×2**，音量仍为 10，轮播仍为 9 秒 ——
只有 `FeatureManager` 的功能开关被恢复，`AppSettings` 无人回滚。
客户现场无法区分「这个值是 U 盘下发的还是运维设的」，
只能整机重置设置才能回到出厂状态。

修复：
- 新增 `data/repository/UsbConfigOverrideStore.kt`
  - `applyOverrides()`：记录被改动的 `键 / 原值 / U 盘写入值`
  - `revert()`：**只回滚「当前值仍等于 U 盘写入值」的键** ——
    运维在设置页手动改过的不动（否则等于替客户做决定）
  - 快照存进同一个 DataStore 的独立 key，进程被杀后仍可回滚
- `MainViewModel`：应用配置后写快照；拔盘与「冷启动时无 U 盘配置」两条路径触发回滚

实测（API30 + bind-mount 假 U 盘）：

| 阶段 | 界面 | DataStore |
|---|---|---|
| 插入后 | 布局 1×2，帮助提示消失 | `layout_mode=GRID_1X2`、`default_volume=10`、`interval=9` |
| 拔盘后 | **布局回到 2×2**，帮助提示恢复 | `GRID_2X2` / `100` / `5`，快照 key 已清除 |

单测新增 7 个用例，其中最关键的是
`revert keeps values the operator changed manually`。

### 缺陷 5（已修）：U 盘拷贝跨播放器不原子（可能留下混合代次）

**问题**：旧实现**逐路提交** —— player1 暂存成功就立刻改名替换，再处理 player2。
若第 3 路「有内容但暂存失败」（拔盘 / IO 错误 / 空间不足），
1–2 路已提交且旧目录已删除 → 四路进入**混合代次**，且无法回滚。

**修复**：先全部暂存（`.playerN_staging`），四路都成功后再统一提交；
任何一路失败就删掉全部 staging，现有缓存保持原样。

**实测**（API30，U 盘 player1/2/4 有内容、player3 只有 0 字节文件）：

```
Player 0 staged (commit deferred)
Player 1 staged (commit deferred)
Player 2: no source content          ← 0 字节被过滤
Player 3 staged (commit deferred)
Committed player 0 / 1 / 3
Copy all completed: committed 3 players
```

| 格子 | 拷贝前 | 拷贝后 | 判定 |
|---|---|---|---|
| player1 | long30.mp4 | new1.mp4 | ✅ 已提交 |
| player2 | long30.mp4 | new2.mp4 | ✅ 已提交 |
| player3 | long30.mp4 | **long30.mp4** | ✅ U 盘无内容 → 保留旧缓存 |
| player4 | long30.mp4 | extra.mp4 + new4.mp4 | ✅ 已提交 |

无 staging / backup 残留。新增 `TwoPhaseCopyTest`（3 例）固化该行为。

## 二bis、远控链路端到端实测（**首次跑通**）

> 此前所有文档都写着「远控需签名权限，模拟器无法验证」。本轮找到了可行路径。

### 如何突破签名权限

用**同一把 release 密钥**（`.local/signing/app-release.jks`）签了一个测试发送端
（`com.btf.testcmd`，只发广播、收状态，不入交付），装在同一个模拟器上即可通过
`signature` 级权限校验。

过程中踩到两个坑，值得记下：

| 坑 | 现象 | 原因 |
|---|---|---|
| 把权限名传给 `sendBroadcast(intent, perm)` | `Permission Denial … due to sender com.btf.testcmd` | 该参数语义是「**接收方**必须持有 perm」，而 sender 自己没有申请自己声明的权限。receiver 的 `android:permission` 已由系统校验发送方，**不应再传** |
| 用 4 参 `registerReceiver(..., broadcastPermission, ...)` 收状态 | 主应用发状态时 `Permission Denial … requires RECEIVE_PLAYER_STATUS due to registered receiver` | 同理：该参数要求**发送方**持有权限。主应用是用 `sendBroadcast(intent, RECEIVE_PLAYER_STATUS)` 发的（要求接收方持有），注册端应传 `null` |

> 这两条对**接入方**同样适用，已补进 `docs/remote-command-contract.md`。

### 联调注意：sender 与主应用的安装顺序

签名相同（`791e6432…`）仍可能拿不到 signature 权限。实测有效的顺序是：

1. 先装主应用（让权限定义就位）
2. 再装 sender
3. `dumpsys package <sender> | grep SEND_PLAYER_COMMAND` 确认 `granted=true`

若顺序反了，`requested permissions` 里有该权限但 `install permissions` 段为空，
广播会被 `Permission Denial` 拒绝。

**实测结论：`hide` 在 Android 11 上有效**，`moveTaskToBack` 被系统接受并真正把任务移出前台。
之前那条担忧不成立（至少在 API30 上）。仍需在 **RK3568 真机**上复核一次 ——
不同 ROM 对 HOME 应用的处理可能不同。

### 一处已澄清（不是缺陷）

初看 `pause_all` 在「没有正在播放的路」时仍回 `command_success` 像是缺陷。
复核后确认：测试序列里 `play_all` 在前，已把 4 路置为 PLAYING，
所以 `pause_all` 确实有可暂停的对象 —— **行为正确**。
`handlePauseAll` 在 `pauseAll()` 返回 false 时会发 `error 1001`，逻辑是通的。

## 三、SAME（2×2 同画面）实测结果

### 结论先行：从「约 10 秒固定偏差、永不收敛」改善到「≤0.1 秒」

| 阶段 | P1 / P2 / P3 / P4（0.1s 计数） | 判定 |
|---|---|---|
| 改动前（release） | 134 / 241 / 231 / 233 | ❌ 偏差约 10 秒 |
| 仅加「起始对齐」 | 240 / 235 / 227 / 242 | ⚠️ 改善到约 1 秒，但仍漂移 |
| **加「速度纠偏」** | **91 / 90 / 90 / 91** | ✅ **≤0.1 秒** |

### 做了什么

1. **起始对齐**（`PlaybackSync.ALIGN_ON_START`，默认开）
   进入 SAME 模式时 P1 沿用原实例继续播，P2–P4 要重新 prepare（软解约 2 秒），
   等它们 READY 时 P1 已多播数秒。日志实测：
   `P3 偏差 -1401ms → 对齐到 2157ms`、`P2 -1867ms`、`P4 -2205ms`。

2. **速度纠偏**（`PlaybackSync.USE_SPEED_TRIM`，默认开）—— **关键**
   漂移不再用 `seekTo` 追赶，而是把跟随格的 `playbackSpeed` 设为 1.05× / 0.95×，
   进入 ±120ms 窗口后立刻恢复 1.0×。
   `setPlaybackSpeed` **不重新缓冲**，这是它和 seek 的本质区别。

### 为什么这推翻了此前的结论

`INDEX.md` 与 `PlaybackSync.kt` 此前都写着「除非做单解码器多 Surface 的架构改动，
否则别再尝试调参」。那句话对 **seek 方案**成立，但对速度纠偏不成立 ——
这是**手段**层面的改变，不是阈值调参：

| 手段 | 是否重新缓冲 | 代价 |
|---|---|---|
| `seekTo` | ✅ 必然 | 每纠正一次转一次圈 |
| `setPlaybackSpeed` | ❌ 不会 | 音画速率 ±5%，几秒内收敛后复原 |

### 稳定性验证（收敛后 60 秒窗口）

```
seek 纠正次数：0
速度纠偏次数：0
```

即：收敛后完全静止，没有周期性干预。画面持续流畅，无转圈。

### 边界与残余限制

| 项 | 说明 |
|---|---|
| 速度纠偏的可处理范围 | 约 ±3 秒；更大偏差（如刚换源）仍走一次 `seek` 兜底 |
| 循环边界 | 片头/片尾 2 秒内跳过同步（`LOOP_GUARD_MS`），避免把循环重置误判为漂移 |
| `PlaybackSync.enabled` | 现在默认 **true**。**若关闭 `USE_SPEED_TRIM`，必须同时把它改回 false**，否则退回「周期性转圈」 |
| 40 秒以上的视频 | 未在更长时间尺度（>10 分钟）验证，需真机长时间观察 |

> **重要**：`MainScreen` 原来有 `if (!enabled) { PlaybackSync.clear(); return }`，
> 周期同步关闭时会在**进入** SAME 模式时清空注册表，导致起始对齐拿不到播放器。
> 已改为「只有离开 SAME 模式才 clear」。这是让起始对齐真正生效的前提。

## 四、UI 层实测：**推翻了一条静默结论，确认了一条 P0**

### 4.1 U1（P0）：鼠标 Press 被 `mouseDragScroll` 消费 —— **静态成立，但实测未能复现**

审计阶段从 `foundation-1.6.6` 字节码确认：`detectTapAndPress` 调
`awaitFirstDown(flags=3)` → `requireUnconsumed=true`、`pass=Main`。
旧实现在 `Initial` pass 无条件 `consume()` Press，理论上会让子级控件收不到 down。

**但模拟器实测显示：修前鼠标点击设置项是能生效的。**
API 30 上 `input mouse tap` 点击「模式 1 / 模式 2」均正常切换。
（`input tap` 走 touchscreen 源、`input mouse tap` 走 mouse 源，两者都试过。）

因此正确表述是：**这是一个真实的、可证明的事件语义风险，但未在目标设备上观测到失效**。
按代码语义（父级 Initial 消费 → 子级 `requireUnconsumed` 跳过）它应当失效，
差异可能来自：
- `clickable` 与 `detectTapSegures` 的监听器注册顺序（子级 pointerInput 可能先于父级收到 Initial），
- 或 Compose 1.6.6 对同一节点树内 pass 顺序的具体实现。

**处置**：仍然修复（改动只有「不再无条件消费 Press」+「超过 touchSlop 才消费 Move」），
并在 API 30 上回归：
- ✅ 鼠标单击设置项生效（模式 5 → 模式 6）
- ✅ 触摸单击依然生效
- ✅ 鼠标按住拖动仍能滚动（设置页从顶部滚到布局模式区）

> 这条写进 `INDEX.md` 的方法论：**能证明的语义风险不等于已观测的缺陷**，
> 修复时要同时记录「理论依据」与「实测是否复现」，否则会重蹈 P1-26 的覆辙
> （修了一个不存在的问题，还附带了抓不到 bug 的测试）。

### 顺带观察：分隔线视觉不均

截图可见右列分隔线明显比左列粗。原因：
`calculatePlacements` 的 `gap = 2`（px）**加上**每格 `padding(1.dp)` + `border(1.dp)`，
density 160 下 1dp=1px，实际缝宽约 4px，且边缘格还多一圈外框。

该行为在 `QuadPlayerLayout` 有注释说明是刻意为之（余数分配给最后一格以保证无缝隙），
**本轮不修改**；若客户对拼接缝有要求，应作为独立视觉任务处理。
