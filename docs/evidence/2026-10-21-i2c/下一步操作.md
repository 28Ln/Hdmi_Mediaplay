# I2C 问题：下一步操作（给现场工程师）

## 当前已确定的结论

| 结论 | 证据 |
|---|---|
| **I2C 流量 100% 来自「I2C 调试页」** | 播放页 60 秒 = 0 条 timeout；调试页 46 秒 = 30 条 |
| App 播放功能本身完全干净 | 播放页、启动流程均零 I2C 事务 |
| 不是内核挂、不是控制器挂 | 无 hung_task，非 I2C 节点 435ms 正常响应 |
| 只有断电重启能恢复 | 驱动重绑、设备重建、i2cget 直连全部无效 |
| 断电重启后可用约 **203 秒** | 逐秒采样实测 |

## 现在需要你做一个实验（5 分钟，不需要拆机）

### 步骤

1. **拔掉设备电源**，等 10 秒
2. **重新上电**
3. 设备起来后 **打开 App**（会直接进 I2C 调试页）
4. **看 ③ 区，点一下红色的「停止」按钮**
   - 停止后，每秒写 `mode` 会停掉
   - ① 区的 5 秒刷新仍在进行（这是读操作）
5. **观察并计时**，看 ① 区状态什么时候变成「不通」

### 判读

| 结果 | 说明 | 下一步找谁 |
|---|---|---|
| **撑过 3 分钟仍正常** | 每秒写 `mode` 是元凶 | 找我们，改调试页写入策略 |
| **仍在约 3 分钟变坏** | 与写入无关，是拼接板 MCU 自身问题 | 找**拼接板供应商** |
| **点停止后仍很快变坏** | 与调试页流量无关 | 找**拼接板供应商** |

## 如果要点更彻底的对照

点「停止」后，**再点右上角「进入播放」离开调试页**，
这样连 5 秒一次的读也没有了。此时总线上零流量。

- 这样能一直正常 → 确定是调试页流量导致（调试工具的问题，正常使用不受影响）
- 这样仍会坏 → 拼接板 MCU 自身问题

## 给拼接板供应商的材料

如果结论指向拼接板，把这份文件发给厂家：

**`docs/evidence/2026-10-21-i2c/README.md`**

核心三句话：

1. **冷启动后约 203 秒，I2C 从机 0x30 失去应答，之后永久失效。**
2. **同一颗 SoC 上另一个 I2C 设备（i2c-1 的 LT86204）全程正常** —— 主机侧无问题。
3. **解绑驱动后用 `i2cget` 直接访问 0x30 依旧超时** —— 绕开所有软件，硬件层不通。

`ipd` 寄存器值：正常期 `0x80`，`reboot` 后 `0x00`（引脚方向全零，说明外设未上电/未复位）。

## 另一个要提前告知 ROM 厂家的事

**当前 ROM 的 SELinux 是 `Permissive` 模式。**

如果改成 `Enforcing`，App 会**完全读不到 I2C 节点**，
直接报「权限拒绝」而非「总线故障」，排查方向会完全不同。

需要在 ROM 侧补 SELinux 策略，或保持 Permissive。
