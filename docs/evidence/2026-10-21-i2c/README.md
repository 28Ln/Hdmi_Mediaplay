# I2C-4 / 0x30 故障规律研究（2026-10-21 深夜）

设备：RK3568 `776134475d08a030`，Android 11
目标：搞清楚「I2C 一开始正常、运行一段时间后失效、必须重启」这个规律。

## 结论

**本机不存在「先好后坏」的窗口。** 从上电第 2.7 秒起持续故障，
10 分钟内每 30 秒探测一次，**零次成功**。软硬件因素已逐项排除，
故障位于 i2c-4 的**电气层**（SDA/SCL 未被拉高）。

## 一、对照实验（最关键）

同一时刻对两条总线做相同操作：

| 总线 / 地址 | 结果 | 耗时 | 判读 |
|---|---|---|---|
| i2c-1 / 0x38（LT86204，已绑驱动） | `EBUSY` | 286ms | 总线正常 |
| i2c-1 / 0x30（该地址无设备） | `No such device or address` | **265ms** | **总线正常，无设备快速 NACK** |
| i2c-4 / 0x30 | `Connection timed out` | **1206ms** | 总线无信号 |
| i2c-4 / 0x2f | `Connection timed out` | 同 | 整条总线无信号 |
| i2c-4 / 0x31 | `Connection timed out` | 同 | 整条总线无信号 |

**关键点**：正常总线在「地址无设备」时 265ms 内返回 NACK。
i2c-4 连这个都做不到 —— **不是 0x30 单颗从机的问题，是整条总线没信号**。

同时刻 i2c-1 日志持续正常：
```
[776.563640] LT86204: 38 b2 ff 00
[776.564243] LT86204: No change needed for TX channels, RX1=0
```

## 二、已排除的软件因素

| 项 | 证据 |
|---|---|
| **驱动** | 解绑 `hdmi-matrix-ctl` 后用 `i2cget` 直连，仍 `Connection timed out` |
| **App** | 停掉 App 15 秒，内核超时计数仍 +15（每秒一次），来自驱动内部探测 |
| **pinmux** | `pin 138/139 → function i2c4 group i2c4m0-xfer`，配置正确 |
| **时钟** | `clk_i2c4` enable=1 @24MHz，`pclk_i2c4` enable=1 @99MHz |
| **总线速率** | DT `clock-frequency = 0x000186A0` = 100kHz 标准值 |
| **DT 节点** | `pinctrl-0` / `clocks` / `interrupts` / `reg` 齐全 |
| **runtime PM** | `unsupported` / `auto`，未挂起 |
| **节点创建** | 14 个 ABI 节点全部存在（共 21 项），驱动绑定正确 |

## 三、故障特征

- **693 次超时，全部 `ipd: 0x00, state: 1`，零变化**
- 间隔精确 **1.013 秒**（驱动内部定时探测）
- 首次超时在上电第 **2.775 秒**，早于驱动绑定（6.962s）
- 驱动在第 6.962 秒明确报告：
  `hdmi-matrix-ctl 4-0030: bound at 0x30, slave not answering (check wiring/IO level)`

`ipd` 是 I2C IP 的引脚方向寄存器回读值。`0x00` 表示输出方向位全零 ——
引脚未能驱动 SDA/SCL。此前另一台样机报 `ipd: 0x80`（部分引脚有动作），
本机连这个都没有。

## 四、超时时长不稳定

10 分钟监测中单次 `i2cget` 耗时：6.5s / 9.0s / 10.4s / 12.5s / 10.5s /
10.6s / 15.1s / 10.7s / 15.7s / 10.6s / 14.9s / 12.1s / 11.7s / 10.3s / 14.2s

波动 6.4~15.7 秒，且部分请求被外层 timeout 杀掉（无返回）。
对照 i2c-1 的稳定 265ms，说明 i2c-4 的时序本身异常。

## 五、需要硬件方排查

按可能性排序：

1. **上拉电阻** — SDA/SCL 是否有 4.7kΩ 上拉到 3.3V。
   `ipd: 0x00` + 整条总线无 NACK，最指向这里。
2. **接线** — i2c4m0 是 gpio4-10(SDA)/gpio4-11(SCL)，
   确认拼接板确实接在这两个脚上，且没有接错到其它管脚组。
3. **供电** — 拼接板 MCU 是否上电。
4. **地址跳线** — 但注意：即使地址错，总线也应快速 NACK 而非超时，
   所以地址不是主要原因。
5. **总线负载/电容** — 线缆过长、上拉过弱会导致上升沿过缓。

## 六、关于「先好后坏」

用户描述「重启后能好一阵再变坏」，但本次实测未能复现：

- 软件重启（`reboot`）后：t=2.7s → 1350s，**零次成功**
- 解绑驱动后立即裸访问：仍超时
- 10 分钟内每 30 秒探测：全部失败

若「好一阵」确实存在，需进一步确认：
- 是否为**断电重启**（而非 `reboot`，后者外设不断电）
- 是否为**另一台板子**
- 「好」的时候 `cat version` 的实际返回值

## 七、可复现的验证命令

```bash
# 1. 对照：正常总线无设备的耗时（应 <300ms）
adb shell su root i2cget -y 1 0x30 0x00

# 2. 故障总线（应超时）
adb shell su root i2cget -y 4 0x30 0x00

# 3. 看驱动报告
adb shell su root sh -c 'dmesg | grep -E "rk3x-i2c|hdmi-matrix" | tail -20'

# 4. 确认 pinmux
adb shell su root sh -c 'cat /sys/kernel/debug/pinctrl/*/pinmux-pins | grep "pin 13[89]"'
```

## 八、SELinux 部署风险（2026-10-21 新增，**重要**）

本机 `getenforce` = **Permissive**，因此 sysfs 访问被放行。但审计日志显示
应用**确实被拒绝**，只是宽容模式没拦：

```
avc: denied { open } for comm="i2c-sysfs-reade"
  path=".../4-0030/version" scontext=u:r:untrusted_app:s0 permissive=1
```

实测对比（临时 `setenforce 1` 后立刻恢复）：

| SELinux | 结果 | 耗时 |
|---|---|---|
| Permissive | `ENODEV`（等 I2C 超时） | 25.5s |
| **Enforcing** | **`Permission denied`** | **289ms** |

**如果量产 ROM 设为 Enforcing，App 将完全无法访问 I2C 节点**，
表现为「权限拒绝」而不是「总线故障」，排查方向完全不同。

需要在 ROM 侧补 SELinux 策略（`untrusted_app` 允许读写该 sysfs，
或改用 `sysfs_i2c` 标签 + 相应 allow 规则），或保持 Permissive。

注：本次开机 36 条 avc denied 涉及 `/dev/i2c-4`、`/mnt/media_rw`、
`/system/xbin/su` 等，说明这类放行是**普遍依赖**，不止 I2C 一处。

已确认 SELinux 状态**不会随运行时间变化**（开机即 permissive，
日志中无任何自动切换记录），因此它**不是**「先好后坏」的原因。

## 九、驱动 unbind 不会因 reboot 自动恢复（操作注意）

测试中执行过 `echo 4-0030 > .../unbind`，之后 `reboot` 重启，
驱动**仍是未绑定状态**（sysfs 只剩 5 个条目，日志显示 `removed`）。
需要手动重新 bind：

```bash
echo 4-0030 > /sys/bus/i2c/drivers/hdmi-matrix-ctl/bind
```

做故障复现时若发现节点数量异常少，先确认这一点，否则会误判为
「驱动未加载」。

## 十、i2c-4 整条总线无信号（2026-10-21 最终判定）

### 全地址扫描

在 i2c-4 上探测**与 0x30 无关**的常见地址：

| 地址 | i2c-4 结果 | 耗时 |
|---|---|---|
| 0x08 | 超时（无返回） | 12.4s |
| 0x30 | `Connection timed out` | 12~25s |
| 0x50 | 超时（无返回） | 12.2s |
| 0x68 | 超时（无返回） | 12.2s |
| 0x76 | 超时（无返回） | 12.3s |
| 0x77 | 超时（无返回） | 13.8s |
| 0x2f / 0x31 | `Connection timed out` | — |

对照 i2c-1 探测不存在的地址：**265~391ms 返回 `No such device`**。

**结论：i2c-4 上没有任何地址能返回 NACK。**
正常 I2C 总线即使从机不存在，控制器也会在 ~265ms 内收到 NACK。
i2c-4 连 NACK 都没有 —— SDA/SCL 上**没有任何电平变化**。

### 同一毫秒的对照

```
[1554.988709] rk3x-i2c fe5d0000.i2c: timeout, ipd: 0x00, state: 1   ← i2c-4 失败
[1555.259182] LT86204: 38 b0 ff 00                                  ← i2c-1 成功
```

两条总线在同一时刻、同一颗 SoC 上，结果完全相反。
这排除了「SoC 整体 I2C 故障」「时钟问题」「系统负载问题」。

### 驱动自己也确认了

重新 bind 后，驱动 probe 时立即打印：

```
hdmi-matrix-ctl 4-0030: bound at 0x30, slave not answering (check wiring/IO level)
```

驱动层结论与我们完全一致。

## 十一、给硬件方的最终判定

**问题不在 0x30，也不在软件。i2c-4 这条总线物理上没有信号。**

i2c4m0 使用 **gpio4-10(SDA) / gpio4-11(SCL)**。需要测量：

1. **上电状态下，用万用表测 gpio4-10 与 gpio4-11 对地电压**
   - 空闲时应为 **约 3.3V**（被上拉电阻拉高）
   - 若为 **0V** → 没有上拉，或线被拉死
   - 若为 **1.65V 左右** → 上拉太弱或存在分压
2. **确认上拉电阻**：SDA/SCL 各需 4.7kΩ 到 3.3V
3. **确认接线**：拼接板是否真的接在 gpio4-10/11（RK3568 的 `i2c4m0` 组）
4. **确认拼接板 MCU 供电**

> `ipd: 0x00` 的含义：I2C IP 的引脚方向寄存器回读值为 0 ——
> 控制器配置的输出方向位**全为零**。这与「总线被拉死/无上拉」
> 的电平表现一致。

### 可以排除的

- ❌ 不是 0x30 地址配置错误（地址错只会 NACK，不会 12 秒超时）
- ❌ 不是驱动问题（解绑后 `i2cget` 直连同样超时）
- ❌ 不是 App 问题（App 停掉后超时照常）
- ❌ 不是 pinmux（`pin 138/139 → i2c4m0-xfer` 正确）
- ❌ 不是时钟（`clk_i2c4` enable=1 @24MHz）
- ❌ 不是 SoC 故障（i2c-0/1/3 同时刻全部正常）

## 十二、读取耗时分布（2026-10-21 补充实测）

对同一节点（`version`）反复测量，耗时**不是固定值**，波动极大：

| 时段 | 耗时序列 |
|---|---|
| 早期 | 10.2s / 5.9s / 5.7s / 5.7s / 5.6s |
| 中期 | 6.5 / 9.0 / 10.4 / 12.5 / 10.5 / 10.6 / 15.1 / 10.7 / 15.7 / 10.6 / 14.9 / 12.1 / 11.7 / 10.3 / 14.2 s |
| 后期 | 25.5s / **40.3s** |
| 本轮连续 8 次 | 9.4 / 9.9 / 9.6 / 9.7 / 6.8 / 5.5 / 5.4 / 5.5 s |
| 对照 i2c-1（无设备） | **0.48s**（稳定） |

### 判读

- 耗时在 **5.4s ~ 40.3s** 之间跳动，跨度 7 倍以上
- 对照总线稳定在 0.48s，说明这不是系统负载或调度问题
- 驱动层超时本该是固定值（由 `clock-frequency` 和重试次数决定），
  **出现如此大的抖动，说明总线上的电气状态在变化**

典型成因：SDA/SCL 被缓慢放电/充电、上拉电阻过大导致上升沿过缓、
或存在漏电流。这些都指向**电气层**，不是软件。

### 与「先好后坏」的关系

用户描述的「重启后能好一阵再变坏」，在电气层完全解释得通：
接触不良 / 电容充放电 / 上拉不足导致的总线状态漂移，
会让总线在「勉强能通」和「完全不通」之间来回。

**建议硬件方重点检查：接触（插拔一次排线）、上拉电阻阻值、以及是否有漏电。**

## 十三、排除 App 的决定性实验（2026-10-21 最终）

```
# App 完全停止（force-stop），清空 dmesg，无人访问 30 秒
dmesg -C
<等待 30 秒>
dmesg | grep -c rk3x-i2c   →  20
```

**App 已停止，30 秒内仍有 20 次 i2c-4 超时。**
超时由驱动自身的定时探测产生，与 App 无关。

### 同一时刻的交替对照

```
[3393.175004] rk3x-i2c fe5d0000.i2c: timeout, ipd: 0x00, state: 1   ← i2c-4 失败
[3393.202263] LT86204: HDMI status=0x44 prev=0x44 ...               ← 27ms 后 i2c-1 成功
[3394.188396] rk3x-i2c fe5d0000.i2c: timeout, ipd: 0x00, state: 1   ← 再次失败
[3394.268861] LT86204: HDMI status=0x44 ...                          ← 再次成功
```

间隔仅 27~80ms 的两条总线，一条稳定失败、一条稳定成功。
这排除了「总线互相干扰」「系统负载」「SoC 时钟」等所有全局因素。

### 周期性特征

dmesg 清空后连续观察，间隔为 1.013 秒或 8.6 秒（有空档），
`ipd` 与 `state` 值**全程无变化**（20/20 都是 `0x00 / 1`）。

若为随机电气噪声，错误类型和耗时应有分布；
实测是**确定性状态** —— 总线从一开始就不在可工作状态。

## 十四、最终结论（可直接转交硬件团队）

| 判定项 | 结论 | 依据 |
|---|---|---|
| App | ❌ 无关 | force-stop 后仍每秒超时 |
| 驱动绑定 | ✅ 正常 | /sys/bus/i2c/devices/4-0030/driver 存在 |
| pinmux | ✅ 正常 | pin 138/139 → i2c4m0-xfer |
| 时钟 | ✅ 正常 | clk_i2c4 enable=1 @24MHz |
| DT 配置 | ✅ 正常 | 100kHz, pinctrl/clocks/interrupts 齐全 |
| SoC | ✅ 正常 | i2c-0/1/3 同时刻全部通信成功 |
| **i2c-4 电气层** | ❌ **异常** | 连 NACK 都收不到（12~40s 超时 vs 对照 0.48s） |

**测量建议**：上电状态，万用表测 **gpio4-10(SDA) / gpio4-11(SCL)** 对地电压。

- **约 3.3V** → 上拉正常，问题在别处（线序、MCU 供电、地址）
- **0V** → 没有上拉电阻，或线路短路到地
- **1.65V 左右** → 上拉过弱，或多个器件分压
- **跳动**（如 0V ↔ 3.3V）→ 接触不良

同时建议：**插拔一次排线**，这是成本最低且最常见的原因。

## 十五、App 侧在长时间故障下的表现（2026-10-21 验收）

修复后的调试页在**持续故障**条件下的实测：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 页面刷新计数 | 卡在 0~1 | **57 次**（持续运行） |
| 总线状态文字 | 「总线挂死」（误报） | 「不通 · 从机无应答（驱动等待超时）」 |
| 原因说明 | 无 | 「节点存在，读取返回 ENODEV → 从机没有 ACK」 |
| 节点列表 | 停在「读取中…」 | **14/14 全显示**，含协议描述 |
| 熔断误触发 | 每次刷新都触发 | **0 次** |
| 冷却自愈 | 无 | 日志可见「熔断冷却结束（34656ms），自动重试一次」 |
| 轮转覆盖 | 无 | 持续推进（`下轮从 cmd_count 继续`） |

**结论**：App 在总线持续无应答的条件下行为正确 ——
如实报告「从机无应答」、不误报为挂死、不卡死界面、不泄漏资源。

这也验证了 2026-10-20/21 系列修复的有效性：
- 区分「驱动慢返回」与「内核挂死」（800ms 初判 + 15s 宽限）
- 节点读串行 + 6s 预算 + 轮转起点
- 熔断 30 秒冷却自愈

现场可直接用该页面判断：若显示「从机无应答（驱动等待超时）」，
即硬件层问题，无需再怀疑 App 或驱动。

## 十六、熔断误判修复后的稳定性验证（2026-10-21）

### 修复前：每 30 秒精确循环误熔断

```
22:50:54  blocked >15800ms — channel tripped
22:51:28  熔断冷却结束（30173ms），自动重试一次
22:51:58  blocked >15800ms — channel tripped
22:52:28  熔断冷却结束（30084ms），自动重试一次
22:52:44  blocked >15800ms — channel tripped
```

根因：读通道单线程，`probeBus` 与 `readAllPresent` 都提交任务，
单节点 5.5 秒 × 队列 3 个 = 16.5 秒 > 15.8 秒阈值。
**排队时间被算进了执行时间。**

### 修复：按「是否已开始执行」区分

任务开始时记 `startedAt`：
- `startedAt == 0`（仍在排队）→ 不熔断，只放弃本次等待
- `startedAt != 0` 且超时 → 真正挂死，熔断

### 修复后：5 分钟连续监测

| 时间 | 熔断次数 | 累计轮次 |
|---|---|---|
| 04:50:47 | **0** | 5 |
| 04:51:47 | **0** | 9 |
| 04:52:48 | **0** | 13 |
| 04:53:49 | **0** | 15 |
| 04:54:50 | **0** | 19 |

页面同时显示：刷新 24 次、内存 255MB、线程 54、状态文字
「不通 · 从机无应答（驱动等待超时）」，14/14 节点全列出。

### 一点分析：App 占 I2C 流量多少

60 秒内 3 轮读取，每轮 2 次事务（probeBus.version + readAllPresent）= 6 次；
同期内核记录 53 次超时。**App 仅占 11%，其余 89% 来自驱动自身的定时探测。**

这也说明：进一步优化 App 侧冗余读（`version` 被读两次）收益有限，
且会把总线判定依赖到不确定的预算分配上，风险大于收益 —— 故未采纳。
